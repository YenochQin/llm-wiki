# Recording Selected Ideas

Read this reference only after Phase 5 has an authorized, nonempty write selection. Paths and commands below are relative to the llm-wiki repository root unless an external root is explicitly named.

1. **Write selected top ideas** (status: proposed):
   For proposed ideas in `write_selection` only:
   ```shell
   # generate slug
   uv run python -X utf8 tools/research_wiki.py slug "<idea-title>"
   ```
   Create `wiki/ideas/{slug}.md` **following docs/runtime-page-templates.en.md (§ideas) exactly** (all fields required; `lint.py` enforces `status` and `priority`):
   ```yaml
   ---
   title: "<idea title>"
   slug: "<idea-slug>"
   status: proposed
   origin: "ideate: <short description of the driving gap / weak claim / paper>"
   origin_gaps: []           # [[claim-slug]] list — claims or topics this idea targets
   tags: []                  # 2-5 topic tags (inherit from target claims / direction)
   domain: ""                # NLP / CV / ML Systems / Robotics (inherit from direction)
   priority: 3               # 1-5 — see Priority computation below
   pilot_result: ""          # empty until reported experimental findings are discussed and recorded
   failure_reason: ""        # empty for proposed ideas
   linked_experiments: []    # empty until user-requested experiment records are added
   date_proposed: YYYY-MM-DD
   date_resolved: ""         # empty until validated/failed
   ---
   ```

   **Priority computation** (maps Phase 4 signals into the 1-5 scale):
   - If `--skip-validation`: default `priority = 3`
   - Otherwise start from `novelty_score` (1-5 from /novelty)
   - `+1` if `gap_alignment_bonus > 0` (directly targets a gap_map entry)
   - `-1` if an actual `review_score <= 4` (major issues downgrade); an unavailable novelty score uses provisional `priority = 3`, clearly labeled unverified
   - Clamp to `[1, 5]`

   **Body sections** (exactly match docs/runtime-page-templates.en.md (§ideas) — do not rename):
   ```markdown
   ## Motivation
   Which gap / weakly_supported claim / paper limitation drives this idea. Cite existing wiki pages with `[[slug]]`; include the source-ledger entries for external grounding here, with ordinary links and `external — not ingested` labels.

   ## Hypothesis
   1-2 sentences stating the testable proposition.

   ## Approach sketch
   3-5 sentences on the proposed method. Cite each borrowed component through an existing wiki page or a linked external source from the ledger. Distinguish source-backed facts from the new hypothesis.

   ## Expected outcome
   What success looks like (metric / claim status change), plus the Phase 4 novelty & review summary:
   - Novelty score: N/5 — <one-line reason from /novelty>
   - Review score: M/10 — <one-line summary from /llm-review>
   Use `not run`, `unverified`, or `not selected for validation` instead of a score when that assessment is absent; proposal status does not mean experimental validation.

   ## Risks
   Feasibility rating (high/medium/low) + top 2-3 risks. Include the main weaknesses surfaced by /llm-review.

   ## Pilot results
   (empty — record actual pilot findings after discussing the user-reported experiment results, when requested)

   ## Lessons learned
   (empty — record lessons and any evidence-backed outcome after discussion with the user, when requested)
   ```

2. **Write selected eliminated ideas** (status: failed):
   For eliminated ideas in `write_selection` only, create `wiki/ideas/{slug}.md` using the **same template above**, with these overrides:
   - `status: failed`
   - `priority: 1` (eliminated ideas never block higher-priority work)
   - `date_resolved: YYYY-MM-DD` (today)
   - `failure_reason: "[filter] <specific elimination reason>"` — the `[filter]` prefix distinguishes ideate-stage eliminations from failures established from actual experiment results discussed with the user. Examples: `"[filter] highly similar published work exists: <paper-title>"`, `"[filter] insufficient feasibility: GPU requirements too high"`
   - Body `## Motivation` and `## Hypothesis` should still be filled (so future banlist matching has content); `## Approach sketch` may be brief; `## Expected outcome` and `## Risks` can note why the idea was eliminated
   - Only these saved failed pages become persistent banlist entries; report-only rejections are not persisted.

3. **Add graph edges** only for saved ideas and existing wiki endpoints; maintain required reverse links. External sources stay as ordinary source links until separately ingested. Empty `origin_gaps` and no graph edge are valid in cold-start mode. Skip commands whose target does not exist:
   ```shell
   # for each idea
   uv run python -X utf8 tools/research_wiki.py add-edge '@configured' --from "ideas/{slug}" --to "claims/{target-claim}" --type addresses_gap --evidence "Generated by ideate"

   uv run python -X utf8 tools/research_wiki.py add-edge '@configured' --from "ideas/{slug}" --to "papers/{source-paper}" --type inspired_by --evidence "Inspired by method in {paper-title}"
   ```

4. **Rebuild derived data** only after actual page/graph changes:
   ```shell
   uv run python -X utf8 tools/research_wiki.py rebuild-context-brief '@configured'
   uv run python -X utf8 tools/research_wiki.py rebuild-open-questions '@configured'
   ```

5. **Append log** after actual writes, using saved proposed/failed counts separately from report-only candidates:
   ```shell
   uv run python -X utf8 tools/research_wiki.py log '@configured' "ideate | saved proposed={P} failed={F} total={P+F}/{max-ideas}; report-only={R} | direction: {direction}"
   ```
